# Spec: build-in-public

## Purpose

Kiruk operates as a transparent studio. Process, decisions, sketches, dead ends, learnings, and shipped work are public artifacts. Revenue figures, client identities (unless permission is given), customer data, contracts, and per-engagement financial terms stay private. This capability defines the boundary, the cadence, and the redaction rules so transparency is a discipline — not a leak.

## Domain vocabulary

| Term                          | Meaning                                                                                                                                                               |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Open**                      | Content intended for public reading: devlogs, manifestos, case studies, ISM ships, product launches, code, specs, sketches.                                           |
| **Closed**                    | Content that MUST NOT be published: revenue numbers, MRR/ARR, customer lists, contracts, signed agreements, raw client briefs, per-engagement budgets, personal data. |
| **Per-universe transparency** | Each client universe may opt into deeper transparency (named case study, raw process visible). Default is closed-on-identity, open-on-process.                        |
| **Story drop**                | A scheduled, narrative-shaped public update (quarterly retrospective, milestone post). Not real-time dashboard; curated.                                              |

## Requirements

### Requirement: Open vs Closed boundary is enumerated

This spec MUST maintain a current Open/Closed table (below). Any change to that table MUST go through an OpenSpec proposal because it directly affects what kiruk publishes.

| Category                                          | Default                  | Notes                                                                                           |
| ------------------------------------------------- | ------------------------ | ----------------------------------------------------------------------------------------------- |
| Devlog (process, decisions, dead ends, learnings) | Open                     | Published when there's material progress — no fixed cadence floor (see "Devlog cadence floor"). |
| Sketches, scribbles, pen-and-paper artifacts      | Open                     | The kirukal layer is the brand.                                                                 |
| Code (this monorepo, products, ISM)               | Open                     | License: see `LICENSE`. Exceptions: client-only branches if any (see repo-privacy).             |
| Specs (`openspec/`)                               | Open                     | Truth is public.                                                                                |
| ISM experiments                                   | Open                     | Including failed ones.                                                                          |
| Product launches                                  | Open                     | What, why, how.                                                                                 |
| Case studies (client universes)                   | Open with client consent | Default to anonymized "Universe X" if no consent.                                               |
| Client names                                      | Closed unless consented  | Per-universe `intake.md` records consent flag.                                                  |
| Client briefs (raw)                               | Closed                   | Internal-only in `kiruk-projects/<universe>/` unless redacted.                                  |
| Revenue (MRR, ARR, per-project fees)              | Closed                   | Excluded from devlogs. Story-drop summaries allowed (quarterly, qualitative).                   |
| Contracts, invoices, agreements                   | Closed                   | Generated by templates; never committed with real values.                                       |
| Customer data (product users)                     | Closed                   | Lives outside repo per `products` data-boundary requirement.                                    |
| Personal struggles, founder mental state          | Founder's choice         | No spec forces this either way.                                                                 |

#### Scenario: Boundary change requires proposal

- GIVEN a contributor or the founder wants to make a Closed category Open (or vice versa)
- WHEN they edit the table directly without an OpenSpec proposal
- THEN PR review and `brand-consistency-ci` reject the change
- AND the contributor is directed to open `openspec/changes/buildinpublic-boundary-<slug>/`

### Requirement: Devlog cadence floor

There is NO fixed devlog cadence floor. A public devlog entry SHOULD be published whenever there is material progress (a shipped thing, a decision, a dead end worth sharing) rather than on a fixed clock. Entries MUST still live in `content/devlogs/<YYYY-MM-DD>-<slug>.mdx`. Tooling MAY surface how long it has been since the last devlog as **information**, but MUST NOT fail or block on a missed interval.

#### Scenario: Long gap is informational, not a failure

- GIVEN no new devlog has been added in 30 days
- WHEN the cadence check runs (e.g. `scripts/doctor.mjs`)
- THEN it reports the days-since-last-devlog as info
- AND it does NOT fail the run or block any merge

#### Scenario: Devlog still lands in the dated folder

- GIVEN the founder publishes a devlog
- WHEN the file is created
- THEN it is named `content/devlogs/<YYYY-MM-DD>-<slug>.mdx`

### Requirement: Redaction before publish

Any content destined for the open surface MUST be scanned for Closed-category leakage before publish. The scan MUST flag: dollar amounts paired with client names, raw email addresses, API key patterns, unredacted client-only brief language.

#### Scenario: Devlog draft mentions revenue figure

- GIVEN a devlog draft containing `"$8,500 from Acme"`
- WHEN the redaction check runs
- THEN the draft is flagged with the offending line cited
- AND publish is blocked until the line is removed or rephrased qualitatively

### Requirement: Story drops are the only revenue surface

Revenue, MRR, and growth figures MAY appear in public artifacts ONLY through a curated quarterly **story drop** post — qualitative, narrative-shaped, no real-time numbers, no per-client breakdown. Story drops MUST be tagged `kind: story-drop` in MDX front-matter.

#### Scenario: Real-time revenue dashboard rejected

- GIVEN someone proposes a live revenue widget on the website
- WHEN reviewed against this spec
- THEN the proposal is rejected
- AND the reviewer points to story-drop format as the only public revenue surface

### Requirement: Per-universe consent recorded

Every client universe's `intake.md` MUST record a `transparency:` field with one of: `closed` (default), `process-only` (process public, identity anonymized), `named` (full case study with client name, with signed consent).

#### Scenario: Case study publishes without consent flag

- GIVEN a case study draft for `kiruk-projects/<universe>/`
- WHEN the universe's `intake.md` has `transparency: closed`
- THEN the case study cannot be published to `content/case-studies/`
- AND a reviewer is prompted to obtain consent or anonymize
